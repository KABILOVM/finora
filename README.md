# Finora — личный учёт денег

Finora ведёт учёт ваших денег: кошельки (в том числе в разных валютах), категории, расходы, доходы, переводы между кошельками, остатки и курсы валют.
Это сайт, который ставится на телефон как приложение (PWA) и **работает без интернета**: всё сохраняется на устройстве.
Если подключить облако (Supabase), данные сами синхронизируются между телефоном и компьютером.

- Интерфейс только на русском. Пользователей до 5, у каждого **свои** данные — друг друга они не видят.
- Деньги хранятся целыми числами в минимальных единицах (дирамы), поэтому копейки не «плывут».
- Записи не удаляются насовсем: «удалить» значит «скрыть». Это нужно, чтобы синхронизация не теряла данные.

## Два режима

- **Локальный** (по умолчанию, ключей нет): без входа, данные только на этом устройстве. Удобно просто посмотреть приложение. Обязательно делайте резервные копии.
- **С облаком**: вход по почте и паролю, данные синхронизируются. Включается двумя переменными, см. «Подключение облака». Если их нет или в них остались заготовки из `.env.example`, приложение честно работает локально.

## Запуск на своём компьютере

1. Установите [Node.js](https://nodejs.org) версии **22.12 или новее** (подойдёт LTS). Эта же версия записана в `package.json` (`engines`), по ней Vercel выбирает среду сборки.
2. В папке проекта выполните `npm install`. В проекте лежит файл `.npmrc` с настройкой `legacy-peer-deps=true` — она нужна, чтобы установка не спотыкалась о версии пакетов. Ничего менять не нужно.
3. Выполните `npm run dev` и откройте адрес из терминала (обычно http://localhost:5173).

## Подключение облака

Нужно один раз, примерно полчаса. Сделайте по порядку.

**1. Создайте проект Supabase.** Зайдите на supabase.com → New project. Проект должен быть **отдельным, только для Finora**: не берите проект другой системы (CRM и т. п.), иначе наши таблицы и правила добавятся в чужую базу.

**2. Создайте таблицы.** В проекте: SQL Editor → New query → вставьте **весь** файл `supabase/schema.sql` (не кусок!) → Run. Файл можно запускать повторно: ничего не удаляется и не дублируется. Это же — способ обновить уже созданный проект: в конец файла добавляются новые ограничения (сейчас — предельная длина полей `color`, `icon` у кошельков и категорий и `fx_source` у операций), и повторный запуск применит их к существующим таблицам. Если среди старых записей нашлась слишком длинная, файл не упадёт (Postgres выдаст предупреждение, но интерфейс Supabase может его не показать); новые и изменяемые записи ограничение проверяет в любом случае.

**3. Добавьте пользователей.** В приложении регистрации нет, людей добавляете вы:
- Authentication → Users → Add user: почта и пароль, отметьте «Auto Confirm User». Так для каждого (до 5 человек).
- Authentication → Sign In / Providers: выключите «Allow new users to sign up», чтобы посторонние не могли зарегистрироваться.
- Про письма: встроенная почта Supabase шлёт письма только членам команды проекта. Поэтому «Confirm email» лучше выключить (там же) — или подключить свой SMTP в настройках Authentication.
- Названия пунктов в Supabase иногда меняются, ищите похожие.

**4. Скопируйте ключи.** Project Settings → API (в новой панели раздел «API Keys»): нужны **Project URL** и **публичный ключ**: publishable key (раньше назывался anon). Создайте файл `.env` рядом с `package.json` по образцу `.env.example`:

```
VITE_SUPABASE_URL=https://ваш-проект.supabase.co
VITE_SUPABASE_ANON_KEY=sb_publishable_...
```

Эти же две переменные добавьте на хостинг. На Vercel: проект → Settings → Environment Variables. Файл `.env` в git не попадает.

> **Не путайте ключи.** На той же странице есть секретный ключ: `service_role` (в новой панели — «secret»). Он открывает всю базу в обход защиты, а всё, что лежит в `VITE_…`, вшивается в публичные файлы сайта — любой посетитель сможет его прочитать. Класть его в приложение **нельзя**. Если ошиблись: подставьте публичный ключ, пересоберите приложение, а старый секретный ключ считайте утёкшим и замените в панели Supabase. «Проверка облака» (шаг 6) заметит `service_role` в сборке и покажет красную ошибку.

> Если вы уже вели учёт без входа (локальный режим), **до** подключения облака сделайте резервную копию (Настройки → «Резервная копия»). После подключения облака приложение открывает данные аккаунта, а записи «без входа» остаются на устройстве отдельно. При первом входе на «Главной» и в «Настройках» появится плашка «Есть записи, сделанные без входа» с кнопкой «Перенести в аккаунт» — записи переносятся без дублей, а стартовые категории сливаются со стартовыми аккаунта. Если нажали «Не переносить», вернуть эти записи можно только из резервной копии.

**5. Пересоберите и выложите приложение.** Значения вшиваются в приложение при сборке, поэтому после любого изменения переменных нужна новая сборка. Локально: `npm run build`, готовый сайт лежит в папке `dist` (подойдёт любой хостинг с https). На Vercel: Deployments → Redeploy (Vercel сам понимает Vite: команда `npm run build`, папка `dist`). Адреса в приложении вида `…/#/settings`, поэтому настраивать перенаправления на хостинге не нужно.

> **Свой домен Supabase.** Если у проекта не стандартный адрес `….supabase.co`, а свой домен, ничего добавлять руками не нужно: при сборке адрес берётся из `VITE_SUPABASE_URL` автоматически и вписывается в политику безопасности страницы (CSP) в `index.html`: ровно этот адрес по `https` и `wss`, и больше никакие адреса Supabase. Поэтому приложение, которое при XSS попыталось бы отправить данные в чужой проект Supabase, упрётся в запрет браузера. Следствие: сменили `VITE_SUPABASE_URL` — **пересоберите** приложение (`npm run build` или Redeploy на Vercel), иначе браузер заблокирует новый адрес. Если переменных нет или в них заготовки из `.env.example` (локальный режим), адресов Supabase в политике нет вовсе. Адрес, из которого нельзя сделать безопасную запись в политику (например, с `;` или `*` в имени хоста), останавливает сборку с понятной ошибкой.

**6. Проверьте.** Откройте приложение, войдите, затем Настройки → «Проверка облака» → «Проверить». Каждый шаг помечен ✔ (хорошо), ⚠ (замечание) или ✖ (ошибка) и подсказывает, что делать. Кнопка «Скопировать отчёт» нужна, чтобы отправить результат тому, кто помогает с настройкой (в отчёте нет паролей, ключей и почты). Если в Настройках по-прежнему написано «Облако не подключено» — переменные не попали в сборку (вернитесь к шагу 5).

Что делает проверка: смотрит, что сервер отвечает и ключ в сборке не секретный; что вы вошли; что все таблицы и нужные колонки на месте; что свои данные читаются, а чужих не видно; что запись разрешена; что курсы на сервере читаются; сколько записей на устройстве ждут отправки. Для проверки записи в каждую из четырёх таблиц (`settings`, `wallets`, `categories`, `transactions`) отправляется одна **заведомо неверная** строка (пустое имя, сумма 0); сервер обязан её отклонить, поэтому в ваших данных ничего не меняется. Если вдруг строка пройдёт, проверка сама об этом скажет, а строка уже помечена «удалена» и в приложении не видна.

> Важно: облако проверялось только на эмуляторе PostgREST и на PGlite (настоящий Postgres в памяти), **не на живом Supabase**. Поэтому шаг 6 обязателен: он покажет, если что-то в вашем проекте настроено не так.

### Что проверка не умеет

«Все проверки пройдены» значит «всё, что мы можем проверить снаружи, в порядке». Два места снаружи проверить нельзя, поэтому их надо посмотреть самому:

- **Защита строк (RLS): чужие данные закрыты?** Проверка видит утечку, только если сервер показал вам чужую запись. Если вы единственный пользователь с данными, при выключенной защите результат такой же, как при включённой: «чужих записей не видно». Поэтому шаг «Чтение данных» прямо пишет, что подтвердить защиту не может. Убедитесь сами (см. «Как убедиться, что чужие данные закрыты» ниже).
- **Правка уже существующих записей.** Проверка проверяет права на вставку и обновление таблиц, но не пробует менять ваши настоящие записи (это изменило бы данные). Если по ошибке удалили только правило правки (политику `…_update_own`), проверка этого не заметит. Список правил смотрите в SQL ниже.

### Как убедиться, что чужие данные закрыты

Сделайте это один раз после настройки и после любого ручного изменения базы. В Supabase → SQL Editor выполните:

```sql
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
order by tablename;
```

Во всех пяти строках (`categories`, `exchange_rates`, `settings`, `transactions`, `wallets`) в колонке `rowsecurity` должно стоять `true`. То же видно в Table Editor: у каждой таблицы метка «RLS enabled».

```sql
select tablename, policyname, cmd
from pg_policies
where schemaname = 'public'
order by tablename, cmd;
```

Строк должно быть **13**: по `INSERT`, `SELECT` и `UPDATE` у `settings`, `wallets`, `categories`, `transactions` и одна `SELECT` у `exchange_rates`. Меньше — значит, `schema.sql` выполнен не целиком: запустите его заново (весь файл).

Самая надёжная проверка — на живых людях: когда добавите второго пользователя и он внесёт запись, откройте «Проверку облака» у первого. Если шаг «Чтение данных» не написал «ОПАСНО», а в приложении первого нет записей второго, защита работает.

## Проверка после выкладки

После каждой выкладки на хостинг проверьте заголовки ответа. Нужен `curl` (есть в терминале macOS и Linux, в Windows 10/11). Подставьте адрес своего сайта вместо `https://ваш-сайт`:

```
curl -I https://ваш-сайт/
curl -I https://ваш-сайт/sw.js
curl -sI "https://ваш-сайт/$(curl -s https://ваш-сайт/ | grep -o 'assets/[^"]*\.js' | head -1)"
```

Третья команда сама находит имя одного из файлов в `/assets/` на главной странице. Значения ниже взяты из `vercel.json`; на другом хостинге заголовки нужно настроить так же.

| Заголовок | `/` и `/sw.js` | `/assets/…` |
|---|---|---|
| `Cache-Control` | `no-cache` (браузер всегда спрашивает, нет ли новой версии) | `public, max-age=31536000, immutable` (имя файла меняется с каждой сборкой, поэтому его можно хранить год) |
| `Content-Security-Policy` | `frame-ancestors 'none'` | то же |
| `X-Frame-Options` | `DENY` | то же |
| `X-Content-Type-Options` | `nosniff` | то же |
| `Referrer-Policy` | `no-referrer` | то же |
| `Strict-Transport-Security` | `max-age=31536000` | то же |
| `Cross-Origin-Opener-Policy` | `same-origin` | то же |
| `Permissions-Policy` | камера, микрофон, геолокация и т. п. запрещены | то же |

В заголовке `Content-Security-Policy` — **только** `frame-ancestors 'none'` (запрет встраивать приложение в чужую страницу). Остальную политику браузер берёт из тега `<meta>` в `index.html`, собранного под ваш проект. Проверить её:

```
curl -s https://ваш-сайт/ | grep -o "connect-src 'self'[^;]*"
```

В облачной сборке там должны быть `'self'`, ваш адрес Supabase по `https://` и `wss://` и три источника курсов (`www.nbt.tj`, `cdn.jsdelivr.net`, `latest.currency-api.pages.dev`). Знака `*` и чужих адресов Supabase быть не должно. Если вместо вашего адреса пусто — в сборку не попали переменные `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (шаг 5 «Подключения облака»).

Эти значения проверены только на раздаче, которая берёт заголовки из `vercel.json` (тесты `e2e/sec`), а не на настоящем Vercel, поэтому проверку выше стоит сделать самому. Если заголовки другие, значит `vercel.json` не подхватился: он должен лежать в корне проекта, рядом с `package.json`.

## Проверка в браузере (e2e)

`npm run test:e2e` сама собирает приложение в `dist`, запускает его на http://127.0.0.1:4173 и прогоняет сценарии в Chromium на двух «устройствах»: `iphone` (узкий экран) и `desktop`. Первый раз выполните `npx playwright install chromium`. Сценарии лежат в папке `e2e`:

- `e2e/flows` — работа человека с приложением: первый запуск, офлайн, валюты, переводы, правки, резервные копии, фильтры;
- `e2e/pwa` — манифест, сервис-воркер, хранилище, обновление версии;
- `e2e/sec` — безопасность: заголовки и политика безопасности страницы (CSP) в настоящем браузере, облачная сборка с поддельным ключом, права и ограничения в `supabase/schema.sql` (прогоняется в настоящем Postgres в памяти, PGlite, без Docker и без живого Supabase).

Один сценарий или одно «устройство»: `npx playwright test e2e/sec --project=desktop`. Параметры берутся из переменных окружения (`playwright.config.ts`): `E2E_PORT` — порт (по умолчанию 4173), `E2E_DIST` — папка сборки (по умолчанию `dist`), `PW_CHROMIUM_PATH` — путь к своему Chromium. Если запускаете несколько прогонов одновременно, дайте каждому свои порт, папку сборки и папку результатов, иначе они мешают друг другу:

```
E2E_PORT=4200 E2E_DIST=/tmp/finora-dist-a npx playwright test e2e/sec --output=/tmp/finora-results-a
```

Группа `e2e/sec` дополнительно собирает «облачную» сборку с поддельным ключом в папку `SEC_TMP`, а `e2e/pwa` держит свои временные сборки и профили браузера в `PWA_TMP` (по умолчанию обе в временной папке системы). Внешние адреса (курсы, Supabase) в `e2e/sec` и `e2e/pwa` подменяются заглушками, в живой Supabase тесты не ходят.

## Курсы валют

Приложение берёт курсы по очереди из трёх источников: с сервера Finora (таблица `exchange_rates`, если вы развернули функцию ниже), с сайта Нацбанка Таджикистана (nbt.tj) и из открытого интернет-источника. Любой курс можно задать вручную: Настройки → «Курсы валют» → «Свой курс» (он главнее всех остальных). Курс старше 3 суток приложение помечает как устаревший.

Порядок, по которому приложение выбирает курс для итогов: (1) ваш «Свой курс» из Настроек; (2) свежий курс из интернета (не старше 3 суток); (3) курс, который вы **ввели руками при внесении операции** (он запоминается как запасной, на экранах помечен «введён вручную ДД.ММ», итог со знаком «≈»; в Настройках → «Курсы валют» его можно сбросить); (4) устаревший курс из интернета. Введённый в операции курс никогда не перекрывает свежий курс из интернета. Сама операция всегда хранит тот курс, по которому внесена, и потом не переоценивается.

**Формат ответов nbt.tj и интернет-источника при разработке проверить вживую не удалось** (сеть была закрыта), разбор написан по предположению. После первого запуска нажмите Настройки → «Курсы валют» → «Обновить курсы» и **сверьте курс с сайтом Нацбанка**. Если не сходится или не обновляется — задайте свой курс.

Серверная функция `supabase/functions/fetch-rates` — необязательно. Она раз в сутки кладёт курсы в `exchange_rates`, и все устройства читают их оттуда. Как развернуть (подробности и готовый SQL — в комментарии в начале файла `index.ts`):
1. Supabase → Edge Functions → создайте функцию `fetch-rates`, вставьте в неё файл целиком; в настройках функции отключите «Verify JWT».
2. Edge Functions → Secrets: добавьте `CRON_SECRET` — длинная случайная строка без пробелов, не короче 32 символов.
3. Раз в сутки её нужно запускать: через расширения pg_cron и pg_net (SQL есть в начале файла) или любым внешним планировщиком (cron-job.org и т. п.). Время в cron — UTC.
4. Функция и расписание на живом Supabase не запускались — проверьте у себя: в «Проверке облака» шаг «Курсы валют на сервере» должен стать ✔, а «последняя дата» в нём — свежей (проверка берёт самые новые строки). Если дата не меняется несколько дней подряд, расписание не работает.

## Установка на iPhone и Android

- **iPhone (Safari):** откройте сайт → «Поделиться» (квадрат со стрелкой) → «На экран Домой» → «Добавить».
- **Android (Chrome):** меню ⋮ → «Установить приложение» или «Добавить на главный экран».

Когда выходит новая версия, приложение покажет «Доступна новая версия» и обновится только после вашего «Обновить».

## Резервные копии — обязательно

Safari на iPhone может очистить данные сайта, который не открывали около недели. Установленное на экран «Домой» приложение надёжнее, но копии всё равно нужны — особенно в локальном режиме, где данных больше нигде нет.

- Сделать копию: Настройки → «Резервная копия» → «Скачать копию (JSON)». Положите файл в надёжное место (почта, облачный диск, компьютер). Делайте это регулярно, например раз в неделю.
- Вернуть данные: «Загрузить копию (JSON)». Копия объединяется с тем, что уже есть: побеждает более новая версия каждой записи, ничего не удаляется.
- Таблица операций для Excel: «Скачать операции (CSV)».
- Настройки → «Хранилище» → «Защитить данные от очистки», если кнопка есть.
- Настройки → «Проверка данных» ищет операции, которые не попадают в остатки (неверная сумма, нет кошелька). Она ничего не меняет.

## Известные ограничения

- **Правки одной записи на двух устройствах объединяются по частям.** Запись делится на независимые части: у операции это «деньги» (сумма, кошелёк, вид, категория, курс — они всегда едут вместе, чтобы не получилась несогласованная запись), «дата», «заметка» и «удаление». Если на телефоне без сети исправили сумму, а на компьютере поменяли заметку, после синхронизации сохранятся **обе** правки, на обоих устройствах. Если же на двух устройствах правили **одну и ту же часть** (например, обе меняли сумму), остаётся правка, сделанная позже. Проверено на моделях и сервере в памяти (см. «Облако проверено…» ниже). Не закрыто: если часы телефона спешат больше чем на 5 минут и ответ сервера при этом потерялся, правка в редком случае может не доехать, поэтому следите, чтобы на устройствах стояло автоматическое время.
- **iPhone не синхронизирует в фоне.** Данные уходят в облако, пока приложение открыто (при запуске, при возврате в приложение, когда появилась сеть, по таймеру и после каждой записи). Закрыли приложение раньше, чем стало «Всё отправлено в облако» — запись остаётся на телефоне и уйдёт при следующем открытии.
- Формат ответов nbt.tj и интернет-источника курсов не проверен вживую (см. «Курсы валют»).
- Облако проверено только на эмуляторе PostgREST и PGlite, не на живом Supabase (см. шаг 6).
- «Проверка облака» не доказывает, что защита строк (RLS) включена, и не проверяет правило правки существующих записей (см. «Что проверка не умеет»).
- Без сети нельзя войти впервые на новом устройстве. Тот, кто уже входил на этом устройстве, открывает свои данные и без сети.

## Где что лежит

- `src/domain` — деньги, типы, расчёты остатков и курсов
- `src/db` — локальная база на устройстве (Dexie), резервные копии
- `src/sync` — синхронизация с Supabase и «Проверка облака» (`diagnostics*.ts`)
- `src/features`, `src/components`, `src/layout` — экраны и интерфейс
- `src/rates` — загрузка курсов
- `supabase/schema.sql` — таблицы и правила доступа; `supabase/functions/fetch-rates` — загрузка курсов на сервере
- `vite.config.ts` — сборка, PWA и подстановка адреса Supabase в политику безопасности страницы (`index.html`); `vercel.json` — заголовки ответа
- `e2e` — проверки в настоящем браузере (Playwright)
