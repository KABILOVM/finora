# Finora — проверка аутентификации и безопасности

Дата проверки: 2026-10-09. Проверены `index.html`, `supabase-config.js`, `cloud.js`, `app.js`, `supabase-schema.sql`, `sw.js`, `README.md` и `DEPLOY.md`.

## Краткий вывод

В приложении нет собственного auth-сервера. Клиентская библиотека `@supabase/supabase-js` выполняет регистрацию и вход через Supabase Auth. Облачные данные сохраняются как один JSON-снимок в `public.user_finance_state`; PostgreSQL RLS ограничивает доступ строкой, чей `user_id` равен `auth.uid()`.

**Облачная авторизация пока не готова к проверке в реальном окружении:** `supabase-config.js` содержит заглушки `YOUR-PROJECT-REF` и `YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY`. Нужны реальные публичные параметры Supabase, выполненная SQL-схема и проверка через HTTPS. В репозитории нельзя хранить service-role/secret key.

## Компоненты

- `index.html`: загружает Supabase JS v2 с CDN, затем `supabase-config.js`, `cloud.js` и `app.js`.
- `supabase-config.js`: только публичный URL и anon/publishable key.
- `cloud.js`: адаптер auth и синхронизации; экспортирует `window.FinoraCloud`.
- `app.js`: форма входа/регистрации/выхода, ручная загрузка/отправка снимка и локальное сохранение.
- `supabase-schema.sql`: таблица `user_finance_state` и политики RLS.
- `DEPLOY.md`: инструкции развёртывания и ручного теста синхронизации.

## Поток запросов

1. При запуске `app.js` вызывает `FinoraCloud.init()`.
2. `cloud.js` проверяет конфигурацию; если она задана, создаёт клиент Supabase и вызывает `auth.getSession()`.
3. Вход вызывает `auth.signInWithPassword({ email, password })`; регистрация вызывает `auth.signUp({ email, password })`; выход вызывает `auth.signOut()`.
4. Supabase JS сохраняет сессию (`persistSession: true`), автоматически обновляет токен (`autoRefreshToken: true`) и проверяет auth-параметры URL (`detectSessionInUrl: true`). Фактическое внутреннее хранилище определяется библиотекой/окружением; приложение напрямую не пишет access token в собственный ключ `localStorage`.
5. `pullState()` читает `payload, updated_at` из `user_finance_state`, фильтруя `user_id` по ID текущего пользователя.
6. `pushNow()` отправляет `user_id`, `payload`, `updated_at` через `upsert`. RLS независимо проверяет `auth.uid() = user_id` при SELECT/INSERT/UPDATE.
7. `save()` в `app.js` сохраняет состояние под общим ключом `finora-state` в `localStorage` и ставит облачное сохранение в очередь с задержкой 900 мс, если пользователь вошёл.

## Что уже сделано в схеме

- Включён Row Level Security.
- SELECT ограничен `auth.uid() = user_id`.
- INSERT и UPDATE имеют `WITH CHECK (auth.uid() = user_id)`; UPDATE дополнительно имеет `USING`.
- Таблица ссылается на `auth.users(id)` с `ON DELETE CASCADE`.
- В этой версии документация схемы обновлена так, чтобы повторный запуск удалял только три политики Finora перед их пересозданием. Таблица и данные не удаляются.

## Риски и ограничения

### 1. Локальные данные общие для всех аккаунтов на одном браузере

Все аккаунты используют `localStorage['finora-state']`. При выходе состояние не очищается, а после входа в другой аккаунт локальные данные могут остаться видны на устройстве и быть отправлены в облако при последующих изменениях. Это основной риск конфиденциальности на совместно используемом устройстве. До использования несколькими аккаунтами на одном браузере необходимо разделить локальное состояние по ID пользователя либо реализовать явный безопасный переход между локальным и облачным профилями.

### 2. Первое сохранение и конфликты

Облако хранит один JSON-снимок на пользователя. Параллельное редактирование с двух устройств может привести к перезаписи более старым снимком. Автосохранение вызывается с задержкой; ошибок фоновой синхронизации пользователь может не увидеть сразу — сообщение попадает в `console.warn` и статус адаптера.

### 3. Регистрация

Клиент проверяет наличие email и длину пароля не менее 8 символов. Сильная политика пароля, ограничение частоты попыток и подтверждение email зависят от настроек Supabase Auth. Обработчик интерфейса показывает «Проверь email» независимо от того, вернул ли `signUp` сессию сразу; текст стоит согласовать с настройкой подтверждения email.

### 4. Service Worker и кэш

`sw.js` кэширует оболочку приложения и локальные файлы, но не должен кэшировать приватные ответы Supabase API. Сейчас обработчик пропускает non-GET запросы, а остальные запросы перехватывает широко. При изменении архитектуры нужно исключить запросы к Supabase Auth/REST из общего cache-first обработчика и проверить, что приватные ответы никогда не записываются в Cache Storage.

### 5. Схема/развёртывание

Публичный ключ не является секретом, но его безопасность зависит от RLS. Не добавлять `service_role`/secret key в клиент. Ограничить разрешённые redirect URLs в Supabase Auth доменами приложения. Использовать HTTPS. Проверить, что в `supabase-config.js` нет заглушек перед релизом.

### 6. Финансовая точность

Курсы валют в `app.js` демонстрационные; данные вводятся вручную. Приложение нельзя считать подключённым к банку или источнику актуальных курсов.

## Проверочный список перед реальным использованием

- [ ] Указать реальные Project URL и публичный anon/publishable key.
- [ ] Выполнить `supabase-schema.sql` в проекте Supabase.
- [ ] Включить подтверждение email (если нужно) и настроить redirect URLs.
- [ ] Создать два тестовых пользователя A и B; убедиться, что B не может читать, вставлять или менять строку A через Supabase API.
- [ ] Проверить выход и вход другим аккаунтом на одном браузере; до реализации разделения локального состояния не использовать так с реальными данными.
- [ ] Проверить синхронизацию на двух устройствах, включая конфликтующие изменения и ошибки сети.
- [ ] Проверить экспорт/импорт резервной копии и настроить независимый backup.
- [ ] Убедиться, что в публичном репозитории нет секретов и пользовательских финансовых данных.

## Проверки, выполненные в этой ревизии

- Проверено содержимое клиентской auth-цепочки и RLS-схемы по исходникам.
- Сделана SQL-схема более безопасной для повторного применения: существующие политики с теми же именами удаляются перед повторным созданием; данные таблицы не удаляются.
- Фактический вход в Supabase и межпользовательский RLS-тест не выполнялись, так как в архиве нет реальных параметров Supabase.
